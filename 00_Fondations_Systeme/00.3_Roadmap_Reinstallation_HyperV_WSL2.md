# Principe directeur


Une feature à la fois, validation obligatoire avant d'empiler la suivante. Chaque phase dépend de la précédente — sauter une validation revient à devoir deviner, en cas d'échec, laquelle des 5 couches a cassé quoi.


# Phase 0 — Prérequis (avant toute activation)


✓

Validation

☐

Intel VT-x activé dans le BIOS/UEFI (obligatoire pour Hyper-V et WSL2).

☐

SLAT (Second Level Address Translation) — natif sur i7-1165G7 (Tiger Lake), aucune action requise.

☐

Accès Windows Update confirmé (déjà validé : port 443 ouvert vers update.microsoft.com).

☐

VirtualBox : désinstallé, ou passé en mode compatibilité Hyper-V (v6.x+) si conservé — sinon conflit direct au démarrage des VM.

Réactiver le lancement de l'hyperviseur au boot (mis à off lors de l'audit précédent) :

bcdedit /set hypervisorlaunchtype auto


# Phase 1 — Hyper-V seul (fondation)


Toutes les autres features en dépendent. On ne touche à rien d'autre tant que celle-ci n'est pas validée stable.

Enable-WindowsOptionalFeature -Online -FeatureName Microsoft-Hyper-V-All -All -NoRestart

Redémarrer.

# Phase 2 — WSL2 + Virtual Machine Platform


Les deux features s'activent ensemble, puis un seul redémarrage :

Enable-WindowsOptionalFeature -Online -FeatureName Microsoft-Windows-Subsystem-Linux -All -NoRestart

Enable-WindowsOptionalFeature -Online -FeatureName VirtualMachinePlatform -All -NoRestart

Redémarrer.

wsl --update

wsl --set-default-version 2

wsl --install -d Debian

⚠ POINT DE VIGILANCE — WSL2 nécessite la virtualisation matérielle et le support SLAT. Si VirtualMachinePlatform échoue à l'activation, retourner au BIOS avant de chercher une cause logicielle.

# Phase 3 — Windows Sandbox


Enable-WindowsOptionalFeature -Online -FeatureName Containers-DisposableClientVM -All -NoRestart

Redémarrer.

⚠ POINT DE VIGILANCE — Si le Sandbox refuse de démarrer après redémarrage : vérifier bcdedit /enum (hypervisorlaunchtype = Auto), puis redémarrer les services vmcompute et vmms (services.msc) avant toute réinstallation.

# Phase 5 — Outils professionnels


Docker Desktop — installer en backend WSL2 (recommandé, plus léger, compatible avec le lab Kali WSL2 existant), pas en backend Hyper-V seul.

VirtualBox (si conservé) — uniquement en mode compatibilité Hyper-V (≥ v6.x). Sinon conflit direct au démarrage des VM.

Kali WSL2 — réinstaller/reconnecter après validation Phase 2.
