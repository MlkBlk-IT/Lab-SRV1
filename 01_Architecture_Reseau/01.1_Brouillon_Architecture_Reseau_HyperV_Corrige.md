# 1. Architecture Réseau



## 1.1 Topologie et Conception Théorique


L'architecture repose sur un modèle à double NAT pour isoler strictement l'infrastructure virtuelle du réseau physique de l'hôte, tout en permettant un accès contrôlé à Internet.

• NAT 1 (Physique) : Routeur/Box FAI gérant le réseau de l'hôte Hyper-V (ex: 192.168.1.0/24).

• NAT 2 (Logique) : Windows Server 2025 agissant comme routeur/pare-feu via RRAS pour le réseau interne des VMs (192.168.50.0/24).


## 1.2 Schéma d'Architecture (ASCII)


[ INTERNET ]            |   [ ROUTEUR PHYSIQUE / FAI ]  <-- NAT 1 (192.168.1.0/24)            |   [ HÔTE HYPER-V (Windows 11/Server) ]      |-- vSwitch_WAN (External) <--- Lié à la carte physique      |   [ WINDOWS SERVER 2025 (SRV1 / DC / Routeur) ]      |-- NIC 1 (WAN) : 192.168.1.50 (vSwitch_WAN)      |-- NIC 2 (LAN) : 192.168.50.1   (vSwitch_LAN)      |   [ Rôle RRAS : Traduction NAT (NAT 2) ]      |   [ vSwitch_LAN (Internal) ] <--- Isolé de l'hôte physique      |      +-------+-------+-------+-------+      |       |       |       |       |   [ubuntu] [win10] [win11] [parrot] [VMn]  <-- Clients (192.168.50.10+)


### Note personnelle – Validation topologique


⚠ Cette version corrige le sous-réseau interne qui était erronément documenté en 10.0.0.0/24. Les captures DNS et DHCP du lab confirment l'utilisation effective du segment 192.168.50.0/24. Cette erreur initiale aurait pu induire en erreur tout audit réseau ou script d'automatisation.


# 2. Configuration Hyper-V & WinNAT



## 2.1 Configuration des vSwitches


Deux commutateurs virtuels ont été déployés pour séparer les flux :

vSwitch_WAN (External) : Permet au Windows Server 2025 d'accéder au réseau physique et à Internet.

vSwitch_LAN (Internal) : Réseau purement virtuel. L'hôte physique n'a pas d'adresse sur ce segment, garantissant une isolation totale.


## 2.2 Configuration WinNAT (Hôte Hyper-V)


Si l'hôte Hyper-V nécessite lui-même un NAT pour des conteneurs ou des services spécifiques, WinNAT est utilisé. Pour les VMs, le NAT est délégué à RRAS sur le WinSrv2025.

Audit Preflight & Configuration WinNAT (PowerShell) :

# Vérification de l'état du service WinNATGet-Service SharedAccess | Select-Object Status, StartType# Configuration du NAT pour le vSwitch_WAN (si requis pour l'hôte)$NatNetwork = "192.168.100.0/24" # Exemple de plage interne hôteNew-NetNat -Name "Host_WAN_NAT" -InternalIPInterfaceAddressPrefix $NatNetwork# Vérification des bindingsGet-NetNat | Format-Table Name, InternalIPInterfaceAddressPrefix -AutoSize


### Note personnelle – Choix du double NAT


Le choix du double NAT n'est pas anodin : il isole totalement le lab des scans réseau de la box FAI et permet de faire tourner un contrôleur de domaine (AD DS) sans risque de conflit DNS avec le resolver du routeur physique. C'est une approche que je systématise sur tous mes labs d'entreprise.


# 3. Déploiement Windows Server 2025



## 3.1 Installation et Mise à Jour


OS : Windows Server 2025 Datacenter Edition (Desktop Experience).

Build initiale : 26100.1742.

Mise à jour cumulative : Application du KB correspondant à la build 26100.33158 via WSUS/Windows Update pour corriger les vulnérabilités critiques et stabiliser les rôles réseau.


## 3.2 Agrandissement VHDX et Partitionnement


Le disque virtuel initial étant sous-dimensionné, une extension a été réalisée.

Étape 1 : Extension du VHDX (Côté Hôte Hyper-V)

# Arrêt de la VM pour sécuritéStop-VM -Name "WinSrv2025-Core"# Extension du disque de 50 Go supplémentairesResize-VHD -Path "C:\VMs\WinSrv2025-Core\Virtual Hard Disks\OS.vhdx" -SizeBytes 100GBStart-VM -Name "WinSrv2025-Core"

Étape 2 : Extension de la partition (Côté Guest OS)

Problème rencontré : La partition de récupération (Recovery) bloquait l'extension de C: via l'interface graphique.

Résolution : Utilisation de diskpart pour manipuler les identifiants de partition ou supprimer/recréer la partition de récupération à la fin du disque.

DISKPART> list diskDISKPART> select disk 0DISKPART> list partitionDISKPART> select partition 3 (Partition Recovery bloquante)DISKPART> delete partition overrideDISKPART> select partition 2 (Partition C:)DISKPART> extend


### Note personnelle – Gestion du stockage


J'ai appris à la dure que Windows Server 2025 place systématiquement la partition Recovery en fin de disque, même lors d'une installation from-scratch sur VHDX. Sur une VM de production, je recommande désormais de provisionner directement 80-100 Go à la création, ou d'utiliser des disques dynamiques avec un maximum élevé. Cela évite l'intervention manuelle en diskpart qui reste risquée.

L'installation a été scriptée via PowerShell pour garantir la reproductibilité, avec des vérifications ponctuelles via le Gestionnaire de serveur (GUI).

### Note personnelle – Automatisation PowerShell


J'ai volontairement conservé netsh pour la partie RRAS car le module PowerShell natif de Server 2025 est encore instable sur certaines builds Insider. En production, je préfère la stabilité d'un outil déprécié mais éprouvé à la nouveauté d'un cmdlet qui peut changer de syntaxe d'un mois sur l'autre. C'est un choix conservateur, mais il a évité bien des mauvaises surprises lors des redémarrages de service.


# 5. Défis Techniques & Résolutions



## 5.1 Espace disque insuffisant & Partition Recovery


Symptôme : Impossible d'étendre le volume C: au-delà de la partition de récupération Windows via diskmgmt.msc.

Cause racine : Windows place la partition Recovery à la fin du disque lors de l'installation, empêchant l'extension contiguë de C:.

Résolution : Suppression de la partition Recovery via diskpart (delete partition override) car elle n'est pas strictement nécessaire sur une VM (les instantanés Hyper-V gèrent la récupération), suivie de l'extension de C:.


## 5.2 Interface Graphique RRAS Dépréciée


Symptôme : Le nœud 'Routage et accès distant' dans la GUI de Windows Server 2025 est absent ou non fonctionnel pour la configuration NAT.

Cause racine : Microsoft a déprécié la console MMC de RRAS dans les dernières builds de Server 2025 en faveur de l'administration PowerShell et netsh.

Résolution : Configuration du routage NAT via PowerShell :

Install-RemoteAccess -VpnType RoutingOnly# Configuration de l'interface NATnetsh routing ip nat add interface "vEthernet (LAN)"


### Note personnelle – Frustration & pragmatisme


La suppression de la console RRAS GUI dans Server 2025 m'a fait perdre près d'une heure. J'ai cherché dans les composants optionnels, les RSAT, les features on-demand… pour finalement comprendre que c'était un choix architectural de Microsoft. Leçon retenue : toujours vérifier la liste des features dépréciées avant de monter une maquette sur une build récente. Cela m'a aussi poussé à documenter chaque commande netsh équivalente, ce qui, au final, rend le déploiement plus reproductible.


# 6. Validation & Tests


Un plan de test rigoureux a été exécuté pour valider chaque couche du modèle OSI et chaque rôle.


## 6.1 Connectivité Réseau & NAT


Test : Ping depuis une VM Client vers 8.8.8.8 et google.com.

Résultat : Succès. Le double NAT fonctionne correctement. Le traçage (tracert) montre le passage par la passerelle 192.168.50.1 puis la sortie vers le réseau physique.


## 6.2 DHCP Leases


Test : Démarrage d'une VM cliente en DHCP. Vérification de l'APIPA, puis de l'attribution.

Résultat : Bail obtenu en < 2 secondes. Vérification côté serveur : Get-DhcpServerv4Lease -ScopeId 192.168.50.0 confirme l'attribution.


## 6.3 Résolution DNS


Test : nslookup srv1.lab.local et nslookup www.microsoft.com depuis une VM.

Résultat : Résolution interne (AD) et externe (Forwarders configurés vers 1.1.1.1 et 8.8.8.8) fonctionnelles.


## 6.4 Partage SMB Multi-VMs


Test : Montage du partage \\srv1.lab.local\Data depuis 3 VMs différentes simultanément. Création, modification et suppression de fichiers.

Résultat : Accès concurrentiel validé. Les permissions NTFS et les partages SMB sont correctement appliqués.


### Note personnelle – Checklist de validation


Je valide systématiquement quatre points avant de considérer un lab 'opérationnel' : (1) résolution DNS interne ET externe, (2) bail DHCP renouvelable après un redémarrage du serveur, (3) tracert qui montre bien les deux sauts de NAT, et (4) accès SMB avec authentification Kerberos. Si un de ces quatre éléments échoue, je ne passe pas en production. C'est une discipline que j'ai adoptée après avoir découvert en pleine démo qu'un forwarder DNS avait été écrasé par une GPO.

## 7.3 Résumé de l'Architecture Finale


L'infrastructure est stable, entièrement documentée et scriptée. L'isolation réseau via le double NAT garantit la sécurité du laboratoire tout en permettant un accès Internet fluide pour les machines virtuelles. Les problèmes liés aux limitations de l'interface graphique de Server 2025 et au partitionnement ont été contournés avec succès via l'automatisation PowerShell et les outils en ligne de commande natifs.


### Note personnelle – Fierté & vigilance


Ce lab est le fruit de plusieurs itérations. Chaque échec – partition bloquée, console RRAS manquante, forwarder DNS oublié – a été transformé en procédure documentée. C'est cette rigueur qui fait la différence entre un 'ça marche chez moi' et une infrastructure reproductible en production. Je suis particulièrement satisfait du temps de bail DHCP (< 2s) et de la stabilité du NAT après 48h de stress-test.


# 8. Annotations Personnelles – Réflexions d'Architecte



## 8.1 Pourquoi j'ai choisi Hyper-V et pas VMware ou VirtualBox


Hyper-V est natif à Windows 11 Pro/Entreprise et offre une intégration parfaite avec les rôles Windows Server. Le switch virtuel externe permet de faire du 'pass-through' réseau sans bidouiller de bridge manuel. De plus, les checkpoints de production et la réplication Hyper-V sont des outils que je maîtrise et qui m'ont déjà sauvé lors de mises à jour ratées.


## 8.2 Le choix de Windows Server 2025 malgré sa jeunesse


Adopter une version 'bleeding edge' comme Server 2025 en mai 2024 (build 26100) était un pari. Le risque était la stabilité des rôles réseau. Le gain était de monter en compétence sur la nouvelle stack avant que les clients ne migrent. Ce pari a été gagnant : j'ai déjà identifié trois comportements dépréciés (RRAS GUI, netsh firewall, SMB1 par défaut off) qui me permettront d'anticiper les projets de migration 2025 de mes futurs clients.


## 8.3 Ce que je ferais différemment la prochaine fois


• Provisionner 100 Go dès le départ pour éviter l'intervention diskpart.• Créer un template VHDX 'sysprepé' de Server 2025 pour cloner le DC en 5 minutes.• Automatiser la création des vSwitches et des VMs via des scripts PowerShell déclaratifs (Infrastructure as Code).• Mettre en place un monitoring minimal (Prometheus + Grafana sur la VM ubuntu) pour surveiller la charge du NAT et les leases DHCP.


## 8.4 Compétences acquises et consolidées


• Administration avancée de Windows Server 2025 (rôles DHCP, DNS, RRAS/NAT).• Gestion du stockage virtuel Hyper-V (VHDX, resize, diskpart).• Résolution de conflits DNS et configuration de forwarders.• Écriture de scripts PowerShell reproductibles et idempotents.• Documentation technique structurée pour audit et transfert de compétences.


## 8.5 Contexte d'utilisation de ce lab


Ce laboratoire sert de banc d'essai pour :• Tester des GPO et des scripts de déploiement logiciel avant application en production.• Simuler des attaques réseau (le Parrot OS est mon Kali-like dédié) et valider la segmentation.• Former des alternants et des stagiaires sur l'administration Windows Server dans un environnement isolé et sans risque.• Préparer la certification AZ-800 (Administering Windows Server Hybrid Core Infrastructure) en ayant une infrastructure réelle sous la main.
