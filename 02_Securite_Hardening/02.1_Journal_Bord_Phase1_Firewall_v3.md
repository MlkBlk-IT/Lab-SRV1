# 1. Objectif de cette phase


Durcir le pare-feu de SRV1 pour isoler totalement l'hôte physique (laptop) du lab, tout en gardant les services essentiels (DHCP, DNS, RRAS) fonctionnels pour les VMs du LAN.


# 2. Ce qu'on a découvert (audit avant action)


Avant de lancer le script de durcissement, un audit réseau a été fait sur l'hôte et sur SRV1. Il a révélé plusieurs écarts entre la documentation existante et la réalité :

Le vSwitch_WAN est de type Internal (pas External comme documenté), et utilise le service ICS/SharedAccess de Windows — plage réelle 192.168.137.0/24, pas 192.168.1.0/24.

SRV1 n'a PAS de contrôleur de domaine actif (AD DS non installé), malgré une documentation antérieure qui le présentait comme un DC opérationnel.

IIS (Web-Server) et Windows Admin Center sont installés sur SRV1 sans avoir jamais été documentés.

Le script de durcissement lui-même (IPs hôte 192.168.137.1 et 10.0.0.0/24) s'est avéré correct — c'est la documentation d'architecture qui était fausse sur ce point.

Leçon retenue : auditer avant de documenter, pas l'inverse. La documentation sera reconstruite en version 4 sur la base de l'état réel confirmé.


# 3. Action réalisée


Exécution du script 06-Durcissement-SRV1-Strategique_v3.ps1 sur SRV1, le 31 juillet 2026.


## 3.1 Changements appliqués


Politique pare-feu : Block Inbound / Allow Outbound sur tous les profils (Domain, Private, Public).

ICMPv4 autorisé uniquement depuis le LAN (192.168.50.0/24).

Hôte physique bloqué en entrée : 192.168.137.1 et 10.0.0.0/24 (Wi-Fi hôte).

Ports bloqués en entrée : RDP (3389), WinRM (5985/5986), SMB (445), NetBIOS (137/138/139).

Sauvegarde automatique avant/après (fichiers .wfw) dans Desktop\SRV1-Hardening-Backups (SRV1 n'a pas de lecteur D:).

# 4. Problème détecté après coup et correction décidée


Un partage SMB de test (C:\Lab-share) avait été créé sur SRV1 pour Win10/Win11 avant le durcissement. La règle Block SMB le rend inaccessible depuis le LAN.


## 4.1 Décision


Le partage ne sera PAS ré-autorisé sur SRV1, même restreint au LAN. SRV1 est le cœur du lab (DHCP/DNS/RRAS) et ne doit porter aucun service optionnel exposé — même en interne — pour rester une cible minimale.

Le partage de fichiers sera migré vers une VM serveur dédiée (candidat retenu : Ubuntu, déjà prévue comme serveur applicatif dans l'architecture). Cette VM absorbera le risque fonctionnel, SRV1 reste fermé en entrée.


# 5. Prochaines étapes


Déployer le partage de fichiers sur une VM Linux séparée (Samba).

Installer AD DS sur SRV1, puis évaluer si un re-durcissement du pare-feu est nécessaire.

Officialiser IIS et Windows Admin Center (règles firewall dédiées, scope LAN uniquement) si leur usage est confirmé.

Réécrire la documentation d'architecture (v4) sur la base de l'état réel confirmé par audit.


# 6. Bilan


Points forts : audit systématique avant toute action destructive, rollback automatique en place, détection proactive du conflit SMB, refus d'ouvrir un port sur SRV1 par simple commodité.

Points à corriger : documenter au fil de l'eau (changelog) plutôt qu'après coup, pour éviter les écarts doc/réalité comme ceux détectés cette phase-ci.
